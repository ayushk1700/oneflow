# ONEFLOW: two-week study beta

## Purpose
Find out whether students can start useful focus sessions without help and want to keep ONEFLOW as their new tab. A working build is not evidence of market fit.

## Participants and consent
Recruit 15–20 adult students who study on Chrome or Edge laptops. Include users of other focus tools and students who use none. Invite people yourself; this repository sends no invitations. Explain that this is a beta, feedback is voluntary, there is no telemetry, and they can stop at any time. Never ask for browser profiles, journal exports, API keys or personal task names.

## Before day 1
Finish the publisher contact and public privacy URL. Verify the manual release checks in MARKET_RELEASE_REPORT.md. Prefer store-distributed beta installation; if sharing an unpacked build, explain its manual update process and export a backup first. Provide the tested zip and its checksum, the short demo, and a way to contact the publisher.

## Day 1: observe a first session
Ask: “Use ONEFLOW to begin something you want to study today.” Start a stopwatch when the welcome screen appears. Do not explain the buttons. Note whether they start without assistance, the elapsed time, abandoned steps, and their own description of the product. Ask permission before recording anything. The 30-second setup target is a hypothesis, not a promise.

## Days 2–6: ordinary use
Let participants use the extension naturally. Do not send daily engagement prompts. Give them Tools → Help & feedback → Download feedback as an optional way to describe friction; they decide whether to send the resulting text file. No activity data is collected by the extension for this study.

## Day 7: brief voluntary check-in
Ask whether they still have ONEFLOW enabled; on how many days they used it; what made starting easier or harder; and whether they encountered lost data, unreliable timers, disruptive sounds or slow new tabs. Ask what they would use if ONEFLOW disappeared. Record self-reports as self-reports, never measured retention.

## Day 14: decide what to change
Ask the same questions, then: “Would you keep this as your new tab?” and “What is the one thing you would change?” Ask those who stopped what prompted the decision. Count nonresponses separately. Do not assume silence means continued use.

## Pilot decision criteria
Use these as internal learning thresholds, not industry benchmarks or statistically reliable market claims:
- At least 80% of observed participants start a session without help.
- Median observed setup time is under 30 seconds.
- At least half of all invited participants explicitly say they still use it on day 14; report both the invited and responding denominators.
- No unresolved loss of user data or repeatable timer failure.
- Several participants independently describe the same useful reason to keep it.

If setup fails, fix onboarding first. If people understand it but stop using it, investigate their actual study routine before adding features or paid plans. If reliability fails, stop widening distribution until fixed.
